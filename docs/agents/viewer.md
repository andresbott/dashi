# Viewer — browser stack, assets, the JS contract

The dashboard viewer is **server-rendered HTML** refreshed by a small amount of
vanilla JavaScript. Every widget renders in two independent pipelines: a modern
browser stack (this file) and an image stack for e-ink displays (see
[rendering.md](rendering.md)). The two stacks share only the widget type string
and the config JSON.

## Two render stacks per widget

Each ported widget carries:

- **Image stack** (existing): `image.go` + `image.html` — inline styles, no
  JavaScript. Rendered by `internal/dashboard/static` into HTML consumed by
  litehtml → PNG for e-ink devices. litehtml has **no CSS Grid**
  (`docs/project/litehtml-rendering-reference.md:268`), **no CSS custom
  properties** (`:270`) and no animations/transitions (`:269`), but **flexbox
  is fully supported** (`:143`) and is the layout tool to reach for — floats
  work too. Do not "port away" from flexbox in an `image.html`: page-indicator
  was rewritten from flex to `text-align` on that false premise and it changed
  rendered PNGs.
- **Browser stack** (new): `browser.go` + `browser.html` + optional
  `{widget}.css` + optional `{widget}.js` — Tailwind utilities, CSS custom
  properties, ES modules. Rendered by `internal/dashboard/browser` into HTML
  served directly to browsers.

Example: `internal/widgets/clock/` holds `image.go`, `image.html`,
`browser.go`, `browser.html`, `clock.js` (no CSS — clock is styled purely with
Tailwind). `internal/widgets/sysinfo/` adds `sysinfo.css` for two rules
Tailwind cannot express (a bar-fill transition and a dimmed error state).

Unported widgets implement neither browser interface and fall back to their
image renderer when viewed in a browser (see Registry section below).

## Browser page shell

`internal/dashboard/browser/page.html` is the outer template. It renders:

- `<link rel="stylesheet" href="/_dashi/assets/viewer.css">` — Tailwind output,
  generated by `make viewer-css` (committed to
  `internal/dashboard/browser/assets/viewer.css`)
- `<link rel="stylesheet" href="/_dashi/assets/widgets.css">` — every widget's
  CSS concatenated in type order for deterministic caching; built at startup by
  `browser.Assets`
- `<link rel="stylesheet" href="/_dashi/theme/{theme}.css">` — generated theme
  CSS variables (see Theming section)
- `<style>` containing the dashboard's `custom.css` last, so it wins. The value
  passes through `dashboard.SanitizeCustomCSS`, which neutralises any
  `</style` sequence: html/template applies **no** escaping inside a `<style>`
  element (unlike a quoted attribute, which still gets the attribute escaper),
  so an owner-uploaded stylesheet could otherwise break out and execute. The
  image shell (`master.html`) does the same and places its `custom.css` block
  at the **end of `<body>`** — litehtml resolves equal-specificity rules by
  insertion order, and widget CSS now ships inside each widget's body, so
  anything earlier would lose to the widget's own rules.
- Rows and cells using Tailwind flex/grid with `data-color-mode` on `<html>`
- `<script type="module" src="/_dashi/widgets/{type}.js">` once per widget type
  present on the page that ships JS

Widget HTML is rendered server-side by Go with **values already filled in from
the warm client cache** at page-load time. JavaScript only keeps those values
fresh; it never constructs the initial markup.

## Asset routes: `/_dashi/*`

All browser-stack assets are served under the `/_dashi/` prefix. Routes are
defined in `app/router/assets_dashi.go` and mounted by `attachDashiAssets`:

| Route | Content |
|---|---|
| `/_dashi/assets/viewer.css` | Tailwind output (embedded) |
| `/_dashi/assets/widgets.css` | Concatenated widget stylesheets (built at startup) |
| `/_dashi/assets/dashi.js` | Shared runtime (`poll`, `every`) |
| `/_dashi/theme/{name}.css` | Generated theme CSS variables |
| `/_dashi/widgets/{type}.js` | Per-widget ES module |

**The underscore prefix is mandatory.** Dashboard IDs are six-character
lowercase alphanumerics (`[a-z0-9]{6}`), so an all-alphanumeric prefix like
`/dashi/` or `/viewer/` could be shadowed by a real dashboard ID. The
underscore moves the namespace outside the dashboard-ID alphabet, making
collisions impossible.

## The shared JavaScript runtime

`internal/dashboard/browser/assets/dashi.js` exports exactly two functions:

- **`poll(selector, {url, every, apply})`** — for widgets whose values come
  from an API. `every` is in seconds; the fetch **deliberately does not run on
  load** — Go has already prefilled the page. `apply` is called with `(el,
  data, set)` where `set` is the setter described below.
- **`every(selector, ms, fn)`** — for widgets that update from local state
  (clock). Runs `fn(el)` immediately then on interval.

Widget ES modules import these by absolute URL
(`/_dashi/assets/dashi.js`), so no bundler is involved for viewer JavaScript.
Only Tailwind CSS has a build step (`make viewer-css`).

### The setter contract (D3: JS never constructs markup)

The setter handed to `apply` supports:

- `set(selector, primitiveValue)` — sets `textContent`
- `set(selector, {text: "..."})` — sets `textContent`
- `set(selector, {hidden: true})` — toggles `el.hidden`
- `set(selector, {style: {color: "red"}})` — merges into `el.style`
- `set(selector, {anyAttr: "val"})` — sets attribute

**There is deliberately no `html` option** — the setter API enforces the rule
that JavaScript never constructs markup. Go renders every widget's structure;
JS only updates values. This eliminates drift between a Go template and a JS
renderer producing the same DOM. See `dashi.js:72-87` (the `setter` function).

## Widget folder layout (target state)

```
internal/widgets/clock/
  module.go          widgets.Module wiring, type string
  image.go           litehtml renderer
  image.html         inline-style template
  browser.go         browser renderer + asset embedding
  browser.html       Tailwind template with empty-able value slots
  clock.js           ES module: import { every } from '/_dashi/assets/dashi.js'
  image_test.go  browser_test.go  module_test.go  clock.test.js
```

Ported widgets: **clock** (no CSS), **sysinfo** (ships `sysinfo.css`). The
remaining twelve widgets have not been ported and render through their image
renderers in the browser (expected transition state, not a defect).

Client packages live separately: `internal/weather/`, `internal/market/`,
`internal/swisstransport/`, `internal/sysinfo/`, `internal/xkcd/` hold client
+ cache. `internal/widgets/{name}/` holds module, renderers, templates and
handler. Promote a client to its own `internal/{name}/` package only when a
second consumer appears. Note: `docs/agents/widgets.md` prior to this refactor
claimed a merged layout — that was reverted.

## Widget registration: optional interfaces

Widgets opt into the browser stack by implementing optional interfaces
declared in `internal/widgets/registry.go` (there is no `types.go` in that
package):

```go
type BrowserRenderable interface {
    RenderBrowser(config json.RawMessage, ctx RenderContext) (template.HTML, error)
}

type BrowserAssets interface {
    CSS() []byte  // may return nil
    JS() []byte   // may return nil
}
```

Unported widgets implement neither. `Registry.RenderBrowser` (see
`internal/widgets/registry.go:83-88`) checks the browser map first, then falls
back to `Render` (the image-stack renderer). This is why the browser viewer
works for all 14 widgets while the port is mid-flight.

`RenderContext.EffectivePalette()` (same file) is the one helper widgets
should use to read colours: it returns the context's palette, or
`themes.DefaultPalette(ctx.ColorMode)` when a caller built the context by
hand. Do not re-implement the fallback per widget — the copy-pasted version
always returned the *light* palette, which would render dark-mode previews
with light greys.

## Tailwind CSS build

Tailwind extracts class names from `internal/dashboard/browser/page.html` and
all `browser.html` widget templates, then writes
`internal/dashboard/browser/assets/viewer.css`. Run `make viewer-css` after
changing templates; the output is committed (it is a build artifact, not
generated code).

**Hard rule for widget templates:** no computed or concatenated Tailwind class
names in Go. Tailwind extraction is static, so `class="text-{{.Size}}"` in a
template produces **no CSS** — the class silently does not exist. Put dynamic
values through inline `style` attributes or CSS variables instead. Example:
`style="color: var(--dashi-{{.Color}})"` works if the variable is defined;
`class="text-[color:var(--dashi-fg)]"` is a Tailwind arbitrary-value utility.

## Theming: CSS variables and concrete values

`theme.yaml` gains two optional maps (`colors`, `colorsDark`) over a **closed**
palette key set. Unset keys fall back to built-in defaults
(`paletteLight`/`paletteDark` in `internal/themes/palette.go:30-40`), which equal the values
`internal/dashboard/static/master.html` hardcoded before themes owned colours.
The nine palette keys: `fg`, `muted`, `bg`, `surface`, `border`, `accent`,
`accentFg`, `warn`, `danger`.

The browser stack gets CSS custom properties (`--dashi-fg`, `--dashi-muted`,
...) via `themes.Store.ThemeCSS`, served at `/_dashi/theme/{name}.css`.
Templates write `text-[var(--dashi-fg)]` or `style="color: var(--dashi-fg)"`.

### Fonts in the browser

CSS variables alone are not enough for fonts: a browser cannot use a family it
has never downloaded. `ThemeCSS` therefore also emits an `@font-face` per font
the theme serves, ahead of the variable blocks:

- one per display font in `theme.yaml`'s `fonts:` list, family = the font's
  `name` (this is what `--dashi-font` selects)
- one for the icon font when `icons.type: font`, family =
  `themes.IconFontFamily(theme)` = `icon-font-{theme}` — exactly the family
  widget markup emits (`internal/widgets/weather/static.go`,
  `internal/widgets/swisstransport/static.go`) and the same name
  `app/router/main.go` registers with the litehtml renderer. Without it,
  font-icon themes render tofu in a browser, including on a default install
  via the unported-widget fallback.

Both point at `GET /api/v0/themes/{name}/fonts/{font}`, whose handler resolves
display fonts *and* the `icon-font-{theme}` name through
`themes.Store.FontData`. No `format()` hint is emitted: that route serves
whatever bytes the theme shipped under a fixed `font/ttf` Content-Type, so
browsers must sniff the real format (a theme shipping woff2 would break on a
`format('truetype')` claim). Display fonts win a name collision with the icon
family, which keeps existing URLs stable.

### Page background

The page background is declared as the CSS **`background` shorthand** on
`body` in `webui/viewer/viewer.css`'s base layer, reading
`var(--dashi-page-bg, var(--dashi-bg))`. This must never become a Tailwind
`bg-[...]` utility: those compile to `background-color`, and `--dashi-page-bg`
carries whole background values — `linear-gradient(...)`, `url(...)
center/cover no-repeat` — which are invalid as a colour and are dropped
silently. When changing this, check *what* the generated CSS says, not merely
that CSS was generated (`TestBodyBackgroundUsesTheShorthandNotAColorUtility`
pins it).

Image backgrounds reach the browser as a **URL**, not inlined bytes:
`buildBrowserBackground` (`app/router/middleware_static.go`) maps
`dashboard:`/`theme:`/`shared:` references onto the existing read routes
(`/api/v0/dashboards/{id}/assets/{path}`,
`/api/v0/themes/{name}/backgrounds/{file}`,
`/api/v0/data/backgrounds/{name}`). The dashboard-asset route sits behind the
per-dashboard auth middleware, so protected dashboards stay protected. The
litehtml stack keeps using `buildBackground`, which inlines a data URI and
returns the raw bytes for the canvas — litehtml fetches nothing over the
network, so that path must not be "modernised".

## Page navigation

A multi-page dashboard renders plain `<a href="?page=N">` links at the bottom
of the shell, one per page, the current one marked with `aria-current="page"`
and a filled accent style. Names come from each `dashboard.Page.Name`, falling
back to `Page {n}`. No JavaScript, no arrow-key binding (the deleted Vue
viewer had one; it was not reinstated). Single-page dashboards render no nav.

The e-ink swipe path is entirely separate: `X-Action: swipe_left/right`
redirects to `?page=N` in `serveImageDashboard` and is untouched by this.

The image stack gets concrete hex values through `RenderContext.Palette`
because **litehtml cannot read CSS custom properties** — it has no support for
`var()` (see `docs/project/litehtml-rendering-reference.md:270`). This is why
the same `theme.yaml` source must serve both stacks: one generates variables,
one injects values.

## Root route behaviour

`GET /` on the viewer resolves the default dashboard server-side and redirects.
Logic in `app/router/main.go` (viewer setup, lines 246-260): load
`dashStore.List()`, find the first dashboard marked `default: true`, or fall
back to `list[0]` (the **alphabetically first by name**, because
`dashboard.Store.List` sorts case-insensitively by name at
`internal/dashboard/store.go:274-276`).

An image-type dashboard with display headers still renders a PNG exactly as
before; all other dashboard types render browser HTML. The HTML preview path
(`serveImageHTMLPreview` and `inlineLocalImages`) was deleted in this refactor.

## Widget-CSS rule and scoping enforcement

A widget ships its own stylesheet **only for what Tailwind cannot express**.
Clock ships no CSS (`CSS()` returns nil). Sysinfo ships two rules: a bar-fill
transition (`transition: width 0.3s ease`) and a dimmed error state
(`[data-dashi-error] { opacity: 0.6 }`).

**All selectors must descend from `.dashi-{type}`** to avoid cross-widget
collisions and keep `custom.css` overrides scoped. Widgets that ship CSS carry
a test enforcing this: `internal/widgets/sysinfo/browser_test.go:83-92`
(`TestSysinfoCSSOnlyTargetsItsOwnRoot`). The check rejects any line containing
`{` that does not start with `.dashi-sysinfo`.

## Formatting parity hazard

Because Go prefills values and JavaScript overwrites them on refresh, any value
formatted on both sides must produce **byte-identical output** or the display
visibly jumps. Examples: clock time formats (`formatTime`), sysinfo's
`humanBytes` and `humanUptime`.

Mitigation: both clock and sysinfo carry **parity tests** running identical
value tables on the Go and JS sides. Go is the contract. See
`internal/widgets/clock/clock.test.js` (the `formatTime` parity suite) and
`internal/widgets/sysinfo/sysinfo.test.js` (`humanBytes`, `humanUptime`).

## Known gaps left by this refactor

1. **Font-based icon themes now work; image-type icon themes still do not.**
   Weather's
   `resolveIconHTML` (`internal/widgets/weather/static.go:231-233`) emits `<img
   src="{absolute filesystem path}">`, which only worked because the deleted
   `inlineLocalImages` helper base64-inlined it for the HTML preview. In the
   browser stack, those file paths do not resolve. **The fix belongs to a
   future plan:** browser templates must reference the existing
   `GET /api/v0/themes/{name}/icons/{icon}` route (`app/router/api_v0.go:55`)
   instead of a file path. Do not reinstate `inlineLocalImages` to paper over
   it. (Font-based icon themes, including the embedded default, *were* also
   broken — nothing served the icon font — and are now fixed by the
   `@font-face` rules described under Theming.)

2. **Unported widgets look plain in the browser.** They render through their
   image renderers (inline styles, no Tailwind, litehtml-oriented markup). This
   is the intended transition state (D10 in
   `docs/superpowers/specs/2026-08-17-vanilla-viewer-architecture.md`), not a
   defect. Porting the remaining twelve widgets is a separate plan.

3. **Interval handles are dropped.** `every(selector, ms, fn)` in `dashi.js`
   (`dashi.js:54`) calls `setInterval` and discards the returned id; `poll`
   does the same (`dashi.js:30`) and additionally attaches a
   `visibilitychange` listener to `document` per widget with no way to remove
   it. Nothing can therefore stop a widget's timer. Harmless while a page is a
   static server render, but it becomes a leak the moment something replaces
   widget DOM in place — the planned editor live-preview, which re-renders a
   widget on every config change, would accumulate one live interval per
   render. Fixing it means returning (or registering) the handles and clearing
   them when a root is detached.

4. **Clock prefill and clock ticks use different timezones.** `clock/image.go`
   and `clock/browser.go` format the prefilled time in the **server's** local
   zone; `clock.js` re-renders from `new Date()` in the **browser's** zone. A
   viewer in another timezone therefore sees the time jump on the first tick
   (up to one second later). Deliberately **not** fixed here, because the fix
   is a product decision between: (a) a per-dashboard configured timezone in
   the clock widget's config, passed to both sides — most flexible, needs a
   config field, an editor control and an IANA zone name in a data attribute
   for `toLocaleTimeString({timeZone})`; (b) render everything in UTC —
   consistent and trivial, wrong for most humans; (c) accept browser-local and
   have Go emit no prefill for the time (breaks D4's complete first paint and
   the no-JS story). Pick one deliberately rather than drifting into it.
