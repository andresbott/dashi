Dashi editor — expanding grid

Widgets span columns and rows. Row heights still come from content, like a table.
drop here to add a row at the end

⠿ moves a widget — drop it inside a row band to land there, or into the gap between two bands to insert a new row. Right edge = columns, bottom edge = rows, corner = both. Try making Weather 2 rows tall, then 3.

What gets saved


      
Four numbers per widget and nothing else. Order is meaningless —
      Shuffle stored order and the layout doesn't move.

    


    

      
Heights come from content

      
No pixel unit anywhere. A row is as tall as what's in it, and a widget spanning 2 rows
      makes those two rows share its height — so h means "as tall as the two widgets
      beside me", not "180px". Nothing can be clipped.

      
Cells fill their band, exactly like a <td> does. That's why a short widget
      next to a tall spanning one shows whitespace — the honest table behaviour.

    


    

      
How each renderer emits it

      

        e-ink / litehtml — table with colspan + rowspan
        

      

      

        browser — CSS grid, no filler cells
        

      

      
The empty <td>s are the filler cells: a table needs every grid position
      accounted for. They're generated, never stored — the JSON above has no trace of them.
      Cells covered by a rowspan from above emit nothing at all.

    


    

      
Still unverified

      
This demo uses CSS grid, which distributes a spanning cell's height across
      its rows correctly. Whether litehtml's table code does the same is the open
      question — its docs claim table width calculation and say nothing about row
      height with rowspan. That needs a render against the real image pipeline before you
      commit to this model.

      
Second thing to check: the image widget uses height: 100%, which is
      unreliable inside a content-sized table cell.

    


    

      
Behaviour worth noticing

      
Dropping into the gap inside a spanning widget grows that widget by a row instead
      of splitting it — though if the dropped widget also lands in its columns, the spanner still
      gets pushed down out of the way.

      
Overlaps resolve by pushing down, never sideways. Rows that end up empty collapse.
